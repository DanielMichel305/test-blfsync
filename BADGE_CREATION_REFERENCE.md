# Badge Creation Reference

This is the caller-facing reference for badge definitions in the current API implementation. A badge definition describes **what can be awarded**; the API caller does not award it to a user directly. The server records qualifying activity and creates each user award once the definition is satisfied.

## Endpoint and access

```
POST /v1/badges
Authorization: Bearer <admin-access-token>
Content-Type: application/json
```

Only users whose role is `admin` can create, read, update, retire, or delete badge definitions.

| Outcome | Status |
| --- | --- |
| Created | `201` |
| Invalid request or invalid trigger configuration | `400` |
| Missing/invalid/expired access token | `401` |
| Authenticated user is not an admin | `403` |
| A selected ministry track does not exist | `404` |
| `code` is already in use | `409` |

## Create request fields

Every create request must be a JSON object with the four required fields below. The two optional fields may be omitted.

| Field | Required | JSON type and accepted values | Notes |
| --- | --- | --- | --- |
| `code` | Yes | String, 1–100 characters after trimming | Unique stable identifier for the definition, such as `seven_day_login_streak`. It is not an ID generated by the server. |
| `name` | Yes | String, 1–100 characters after trimming | Human-readable display name, such as `Week of Faithful Login`. |
| `description` | Yes | String, 1–2,000 characters after trimming | Human-readable explanation of the achievement. |
| `triggerKey` | Yes | One of the four exact strings in [Trigger catalogue](#trigger-catalogue) | Selects the event or time condition evaluated for the badge. |
| `requirementConfig` | Yes | Object whose exact shape depends on `triggerKey` | The configuration object is required even when the badge starts inactive. |
| `order` | No | Integer greater than or equal to `0`; default `0` | Display/evaluation ordering. Lower values appear first. There is no upper bound. |
| `isActive` | No | Boolean; default `true` | An active definition is immediately eligible for future evaluation and its code/trigger/configuration become locked. Use `false` to save a draft. |

`id`, `definitionLockedAt`, `createdAt`, `updatedAt`, award data, and evidence are server-generated/read-only. Do not send them. Other unknown top-level fields are currently stripped by request validation, not stored; callers should treat them as unsupported.

### Minimum valid request

```json
{
  "code": "first_login",
  "name": "First Login",
  "description": "Sign in to BetterLife Friends for the first time.",
  "triggerKey": "action.login",
  "requirementConfig": {
    "mode": "rolling_window",
    "count": 1,
    "windowDays": 1
  }
}
```

Because `order` and `isActive` are omitted, this creates an active badge with `order: 0` and a non-null `definitionLockedAt` timestamp.

## Trigger catalogue

`triggerKey` and `requirementConfig` are a required pair. The configuration may not be exchanged between triggers. The table and examples below cover every supported configuration shape.

| Trigger key | Trigger kind | What the server evaluates | Allowed `requirementConfig` shapes |
| --- | --- | --- | --- |
| `ministry.track.duration` | Time | How long an active user has held a ministry-track membership | Any-track duration or a specific-track duration |
| `action.login` | Action | Successful user logins | Consecutive action history or rolling-window action history |
| `action.donation` | Action | Attributed successful donation/payment events | Consecutive action history or rolling-window action history |
| `action.referral` | Action | A referred invitation accepted by the invited person, credited to the referral owner | Consecutive action history or rolling-window action history |

> Note: `action.referral` is supported by the badge trigger registry and request validator. If a generated client relies on the current `openapi.yaml`, add this enum value there on the client side until that file is updated.

### 1. Ministry-track duration: any track

Use this when time spent on **any** qualifying ministry track may earn the badge.

```json
{
  "code": "thirty_days_committed",
  "name": "Thirty Days Committed",
  "description": "Maintain a ministry-track membership for thirty full days.",
  "order": 10,
  "triggerKey": "ministry.track.duration",
  "requirementConfig": {
    "targetDays": 30,
    "trackId": null
  },
  "isActive": false
}
```

### 2. Ministry-track duration: one specified track

Use this when the time must be spent on a particular existing ministry track.

```json
{
  "code": "water_project_sixty_days",
  "name": "Water Project Commitment",
  "description": "Maintain the Water Project ministry-track membership for sixty full days.",
  "order": 20,
  "triggerKey": "ministry.track.duration",
  "requirementConfig": {
    "targetDays": 60,
    "trackId": "11111111-1111-4111-8111-111111111111"
  },
  "isActive": false
}
```

Duration configuration rules:

| Key | Required | Accepted value |
| --- | --- | --- |
| `targetDays` | Yes | Positive integer; `1` means one complete 24-hour day. |
| `trackId` | No in the JSON object, defaults to `null` during trigger validation | `null` for any track, or the UUID of an existing ministry track. |

No other keys are allowed in this configuration. A user satisfies the badge when one matching membership is at least `targetDays` whole days old. A matching membership is not a cumulative total across tracks or separate membership periods.

Time-based badges are evaluated by the monthly scheduler at **00:05 UTC on the first day of each month**. Eligible candidates must be active users and must still have the matching membership record. The API does not expose an endpoint for a caller to force this evaluation.

### 3–8. Action badges

The following two configuration shapes work with each action trigger. Substitute the desired action trigger key exactly as shown in the examples. All numeric fields are positive integers; zero, decimals, strings, and negative values are rejected.

#### Consecutive action history

```json
{
  "code": "seven_login_streak",
  "name": "Seven-Login Streak",
  "description": "Log in seven times without a gap longer than two days.",
  "order": 30,
  "triggerKey": "action.login",
  "requirementConfig": {
    "mode": "consecutive",
    "count": 7,
    "maxIntervalDays": 2
  },
  "isActive": false
}
```

| Key | Required | Accepted value |
| --- | --- | --- |
| `mode` | Yes | Exact string `consecutive`. |
| `count` | Yes | Positive integer number of qualifying actions required. |
| `maxIntervalDays` | Yes | Positive integer. Each adjacent qualifying action in the streak must be no more than this many 24-hour days apart. |

A non-qualifying action resets the streak. A gap strictly greater than `maxIntervalDays` resets it too. This is an action-record streak, not necessarily one action per calendar day: several qualifying actions may share a day, and a 24-hour boundary is evaluated using timestamps.

#### Rolling-window action history

```json
{
  "code": "three_donations_in_thirty_days",
  "name": "Three Donations in Thirty Days",
  "description": "Make three qualifying donations during any thirty-day period.",
  "order": 40,
  "triggerKey": "action.donation",
  "requirementConfig": {
    "mode": "rolling_window",
    "count": 3,
    "windowDays": 30
  },
  "isActive": false
}
```

| Key | Required | Accepted value |
| --- | --- | --- |
| `mode` | Yes | Exact string `rolling_window`. |
| `count` | Yes | Positive integer number of qualifying actions required. |
| `windowDays` | Yes | Positive integer. The selected first and last actions must be no more than this many 24-hour days apart. |

Non-qualifying actions are ignored for a rolling-window calculation rather than breaking it. The time boundary is inclusive: a span equal to `windowDays` qualifies.

#### Complete action trigger/configuration matrix

Use exactly one row as the `triggerKey`/`requirementConfig` pair. The names, code, description, order, and active state remain independently configurable according to the field rules above.

| # | `triggerKey` | `requirementConfig` |
| --- | --- | --- |
| 3 | `action.login` | `{ "mode": "consecutive", "count": 7, "maxIntervalDays": 2 }` |
| 4 | `action.login` | `{ "mode": "rolling_window", "count": 7, "windowDays": 30 }` |
| 5 | `action.donation` | `{ "mode": "consecutive", "count": 3, "maxIntervalDays": 30 }` |
| 6 | `action.donation` | `{ "mode": "rolling_window", "count": 3, "windowDays": 30 }` |
| 7 | `action.referral` | `{ "mode": "consecutive", "count": 3, "maxIntervalDays": 90 }` |
| 8 | `action.referral` | `{ "mode": "rolling_window", "count": 3, "windowDays": 180 }` |

Only the **shape** and data-type constraints in this matrix are fixed; the positive integer values are examples and may be changed to any positive integer when creating an inactive definition.

### Invalid configuration combinations

The trigger registry rejects these with `400`:

| Invalid combination | Why it is invalid |
| --- | --- |
| `ministry.track.duration` with `mode`, `count`, `windowDays`, or `maxIntervalDays` | Those fields only apply to action triggers. |
| An action trigger with `targetDays` or `trackId` | Those fields only apply to ministry-track duration. |
| `mode: "consecutive"` plus `windowDays` | Consecutive mode requires `maxIntervalDays` and rejects `windowDays`. |
| `mode: "rolling_window"` plus `maxIntervalDays` | Rolling-window mode requires `windowDays` and rejects `maxIntervalDays`. |
| Either action mode without `count` | Every action badge needs a positive action count. |
| Unknown key in `requirementConfig` | Trigger configuration is strict; unknown configuration keys are rejected. |
| Unknown `triggerKey` | Only the four exact keys in the catalogue are supported. |
| `trackId` that is malformed or does not identify a ministry track | A specific-track duration badge must point to an existing track. |

## When action triggers occur

The badge-creation caller chooses the rule, not the individual action. The application writes supported actions itself, queues a durable badge-refresh job, and evaluates matching active badges asynchronously.

| Trigger | Qualifying application event | Deduplication behavior |
| --- | --- | --- |
| `action.login` | Successful password login or successful two-factor verification. | Each successful login is recorded as a new action. |
| `action.donation` | An attributed successful payment/donation processed by the Stripe webhook flow for an active user. | The underlying payment identifier is used as the action source, so repeat webhook delivery does not create another action. |
| `action.referral` | An invited user accepts an invitation associated with a referral. The action belongs to the referral owner, not the new user. | The referral ID is used as the action source, so it is recorded once. |

An action can be stored as non-qualifying internally, but badge-definition callers cannot set that value through `POST /v1/badges`. Current production sources above record qualifying actions. Evaluation uses the action event timestamp, so a successful response to the originating action does not imply that the award is already visible; poll the user-badge endpoint if the UI needs to observe the result.

## Activation, editing, retirement, and deletion

Start with `"isActive": false` when an administrator needs to review or revise the rule before it can award anyone. Activate it with:

```
PATCH /v1/badges/{badgeId}
Authorization: Bearer <admin-access-token>
Content-Type: application/json
```

```json
{
  "isActive": true
}
```

The lifecycle behaves as follows:

| State/action | Allowed changes and effect |
| --- | --- |
| Create with `isActive: false` | A draft. It cannot be awarded. `code`, `triggerKey`, and `requirementConfig` may be updated together as needed. |
| Activate a draft | Locks `code`, `triggerKey`, and `requirementConfig` at their current values. The server re-validates the stored trigger configuration. |
| Create with `isActive: true`, or omit `isActive` | Immediately locks `code`, `triggerKey`, and `requirementConfig`. |
| Update a locked definition | `name`, `description`, `order`, and `isActive` may be patched. `code`, `triggerKey`, and `requirementConfig` cannot be patched. |
| Retire | `PATCH /v1/badges/{badgeId}/retire` sets `isActive` to `false` and preserves existing awards. Calling it again is safe. |
| Change a rule after activation | Retire the old badge and create a new definition with a new `code`; the locked rule is never editable. |
| Delete | `DELETE /v1/badges/{badgeId}` only succeeds if the badge is inactive **and** has no user awards. |

For a normal `PATCH /v1/badges/{badgeId}`, send at least one mutable field. If either `triggerKey` or `requirementConfig` is sent for an unlocked draft, both must be sent in the same request.

## Successful create response

The server wraps the complete stored badge definition in `badge`:

```json
{
  "message": "Badge created successfully",
  "badge": {
    "id": "de3b1c31-12a0-4b79-ae49-9c443c0fd583",
    "code": "first_login",
    "name": "First Login",
    "description": "Sign in to BetterLife Friends for the first time.",
    "order": 0,
    "triggerKey": "action.login",
    "requirementConfig": {
      "mode": "rolling_window",
      "count": 1,
      "windowDays": 1
    },
    "isActive": true,
    "definitionLockedAt": "2026-09-15T10:00:00.000Z",
    "createdAt": "2026-09-15T10:00:00.000Z",
    "updatedAt": "2026-09-15T10:00:00.000Z"
  }
}
```

Use `GET /v1/users/{userId}/badges` to read active badge display data plus `earned: true | false`. That response intentionally does not expose the trigger configuration, award timestamp, or internal evidence.

## Server-generated award evidence

`requirementConfig` is the only complex object supplied when creating a badge. When a user earns it, the server stores a separate, read-only evidence object with the award. It is shown here to distinguish it from input data; API callers do not send it in a create request.

Action award evidence has this shape:

```json
{
  "actionKey": "login",
  "mode": "rolling_window",
  "targetCount": 3,
  "actionIds": [
    "f8ea7ec8-862c-4e78-95a7-9c470d3ec3ee",
    "a6a4c6e1-f5eb-4411-b4db-18494f3c6cf9",
    "d10bb4cf-ed35-4db8-b129-56405177d93e"
  ],
  "periodStartedAt": "2026-08-01T08:00:00.000Z",
  "periodEndedAt": "2026-08-03T08:00:00.000Z",
  "evaluatedAt": "2026-08-03T08:00:00.000Z"
}
```

Ministry-track duration award evidence has this shape:

```json
{
  "triggerKey": "ministry.track.duration",
  "ministryTrackId": "11111111-1111-4111-8111-111111111111",
  "membershipStartedAt": "2026-07-01T00:05:00.000Z",
  "targetDays": 30,
  "elapsedDays": 31,
  "evaluatedAt": "2026-08-01T00:05:00.000Z"
}
```

Awards are idempotent: the system enforces at most one award for a given `(userId, badgeId)` pair, even if an event or evaluation is retried.
